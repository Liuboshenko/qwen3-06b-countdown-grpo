## 1. Весь проект в одном абзаце

Берём маленькую готовую языковую модель Qwen3-0.6B и учим её решать арифметическую головоломку Countdown.
Учим не на готовых ответах, а методом "попробуй и получи оценку". Модель пишет 8 вариантов ответа на одну задачу,
программа-проверяющий ставит каждому награду, и модель сдвигается в сторону вариантов, которые оказались лучше
остальных в своей группе. Это GRPO. Саму модель не меняем: обучается маленькая надстройка, LoRA-адаптер.
Исследование - сравнение двух способов ставить награду: строгого (1 или 0) и частичного (до 0.5 за близость к цели).

| Слой | Вопрос | Что это у нас |
|---|---|---|
| Задача | чему учим | Countdown и программа, которая проверяет ответ |
| Метод | как учим | GRPO + LoRA, награда от программы (RLVR) |
| Исследование | что хотим узнать | помогает ли частичная награда или ведёт к reward hacking |

## 2. Схема пайплайна

```
 ЭТАП A. ПОДГОТОВКА (один раз, до обучения)

 +---------------------+      +----------------------+      +----------------------+
 | Генератор задач     |      | Калибровка сложности |      | Замер базовой модели |
 | countdown_data.py   | ---> | calibrate_difficulty | ---> | evaluate.py          |
 | train 3985          |      | на val: база решает  |      | на held-out: 20.3%   |
 | val 200             |      | 27.5% задач          |      | (это "шаг 0")        |
 | held-out 300        |      |                      |      |                      |
 +---------------------+      +----------------------+      +----------------------+

 ЭТАП B. ОБУЧЕНИЕ (150 шагов, для каждого условия и каждого seed)

            +---------------------------------------------------------------+
            v                                                               |
   8 задач из train                                                         |
            |                                                               |
            v                                                               |
   +------------------+   64 ответа   +---------------+   64 награды        |
   | МОДЕЛЬ + LoRA    | ------------> | ПРОВЕРЯЮЩИЙ   | ---------+          |
   | 8 ответов на     |               | reward.py     |          v          |
   | каждую задачу    |               +---------------+  +--------------------+
   +------------------+                                  | GRPO: сравнение    |
            ^          обновление весов LoRA             | внутри группы,     |
            +--------------------------------------------| потери, градиент   |
                                                         +--------------------+
   каждые 25 шагов: оценка на held-out (жадное декодирование)
   каждые 10 шагов: чекпойнт (обучение продолжается после выключения машины)

 ЭТАП C. ОЦЕНКА И АНАЛИЗ

   база и 6 обученных адаптеров -> одни и те же 300 задач held-out -> точность, графики,
   ответы "до и после", ошибки, reward hacking, ответ на исследовательский вопрос
```

## 3. Задача и данные

Даны 3 числа (от 1 до 99) и цель (от 1 до 199). Нужно выражение из `+ - * /` и скобок, где каждое число
использовано ровно один раз, а значение точно равно цели. Пример: числа 3, 7, 25, цель 46, ответ `<answer>25 + 3 * 7</answer>`.

Задачи генерируются в [src/countdown_data.py](src/countdown_data.py) с `DATA_SEED = 42`:

```
 1. выбрать 3 случайных числа от 1 до 99
 2. построить из них случайное выражение (операции и скобки)
 3. значение выражения взять как цель -> задача заведомо решаема
 4. фильтры: цель целая и в диапазоне 1-199, цель не равна одному из чисел и их сумме, задачи не повторяются
 5. контроль: эталонное решение проходит проверяющий
```

Сплиты: train 3985, val 200 (только калибровка сложности и пилот), held-out 300 (только итоговая оценка).
Сплиты не пересекаются. Строже задания: в train нет даже того же набора чисел, что в val или held-out.
Поле `solution` в обучении не участвует, модель эталонных решений не видит.

Сложность подбиралась на val, чтобы база решала 10-50% задач (требование задания): 3 числа 1-99, цель 1-199,
база решает 27.5% на val и 20.3% на held-out.

## 4. Проверяющий и две награды

Код: [src/reward.py](src/reward.py). Ответ модели проверяется за 7 шагов:

```
 1. найти последнюю пару тегов <answer></answer>         нет -> no_answer
 2. заменить символы операций из условия на * / -
 3. только цифры, пробелы, скобки и + - * /              иначе -> forbidden_syntax
 4. разобрать выражение модулем ast (не eval)            ошибка -> parse_error
 5. разрешены только целые числа и 4 операции            иначе (степень, унарный минус) -> forbidden_syntax
 6. мультимножество чисел совпадает с исходным           иначе -> wrong_numbers
 7. точное значение в Fraction равно цели                деление на ноль -> division_by_zero, иначе wrong_value
                                                         всё прошло -> correct
```

Почему `ast`, а не `eval`: `eval` выполнил бы любой код из ответа модели. Почему `Fraction`: во float
`13 / 3 * 27` даёт 116.99999999999999, а не 117.

Две функции награды отличаются только статусом `wrong_value`:

| Статус | `baseline` (строго по заданию) | `partial` (эксперимент) |
|---|---|---|
| `correct` | 1 | 1 |
| `wrong_value` (все правила соблюдены, значение не то) | 0 | $0.5 \cdot \max(0,\ 1 - \lvert v - t \rvert / t)$ |
| любое нарушение правил | 0 | 0 |

Здесь $v$ - значение выражения, $t$ - цель. Все случаи проверяются в разделе 2 ноутбука [countdown_tests.ipynb](countdown_tests.ipynb).

## 5. Модель и LoRA

Модель `Qwen/Qwen3-0.6B`, ревизия зафиксирована по номеру коммита. Режим рассуждений выключен
(`enable_thinking=False`), модель сразу пишет ответ длиной около 16 токенов.

LoRA замораживает исходную матрицу весов $W$ и добавляет поправку из двух узких матриц:

$$h = W x + \frac{\alpha}{r}\, B A x, \qquad r = 16,\ \alpha = 32$$

- $A$ размера $r \times d_{in}$ и $B$ размера $d_{out} \times r$ обучаются, $B$ в начале нулевая,
  поэтому на шаге 0 модель с адаптером в точности равна базе
- адаптеры стоят на 7 типах линейных слоёв во всех 28 слоях модели: 10.09 млн параметров (1.67% модели)
- готовый адаптер - файл около 40 МБ, все 6 лежат на Hugging Face: [liuboshenko/qwen3-0.6b-countdown-grpo-lora](https://huggingface.co/liuboshenko/qwen3-0.6b-countdown-grpo-lora)

Почему LoRA: видеопамяти доступно около 3 ГБ, полное дообучение не помещается. Кроме того, исходная модель
для штрафа KL получается простым отключением адаптера, вторая копия модели в памяти не нужна.

## 6. GRPO: как награда превращается в обновление весов

**Преимущество внутри группы.** На каждую задачу модель генерирует группу из $G = 8$ ответов.
Награда каждого ответа сравнивается со средней наградой группы:

$$A_i = \frac{r_i - \bar r}{s + 10^{-4}}, \qquad \bar r = \frac{1}{G}\sum_{j=1}^{G} r_j$$

где $s$ - стандартное отклонение наград в группе. Ответ лучше группы получает плюс (его вероятность растёт),
хуже - минус. Отсюда название: Group Relative Policy Optimization. Отдельная нейросеть-критик, как в PPO, не нужна.

**Пример.** Числа 3, 7, 25, цель 46. Верного ответа в группе нет:

| Ответ | Значение | r baseline | A baseline | r partial | A partial |
|---|---|---|---|---|---|
| `25 + 7 + 3` | 35 | 0 | 0 | 0.380 | +0.94 |
| `25 + 7 - 3` | 29 | 0 | 0 | 0.315 | +0.52 |
| `25 * 3 - 7` | 68 | 0 | 0 | 0.261 | +0.17 |
| `25 - 7 + 3` | 21 | 0 | 0 | 0.228 | -0.04 |
| `25 + 7 + 3` | 35 | 0 | 0 | 0.380 | +0.94 |
| `25 + 3 * 3` | - | 0 | 0 | 0 | -1.52 |
| `25 + 7 - 3` | 29 | 0 | 0 | 0.315 | +0.52 |
| `(25 - 3) * 7` | 154 | 0 | 0 | 0 | -1.52 |

При строгой награде такая группа молчит: все награды равны, все преимущества нулевые, веса не меняются.
Доля таких групп пишется в лог как `frac_reward_zero_std`. При частичной награде группа даёт сигнал,
и сильнее всего поощряется "сложить все числа" - ответ, который задачу не решает.
Деление на $s$ усиливает даже маленькие различия частичных наград. На этом примере построен исследовательский вопрос.

**Функция потерь в нашей конфигурации.** На каждую порцию ответов делается одно обновление (`num_iterations = 1`),
поэтому ограничитель PPO (clip) не срабатывает (в логах `clip_ratio` равен 0). Градиент имеет простой вид:

$$\nabla_\theta L = -\frac{1}{N}\sum_{i}\sum_{t} A_i\ \nabla_\theta \log \pi_\theta(y_{i,t} \mid x, y_{i,\lt t})\ +\ \frac{\beta}{N}\sum_{i}\sum_{t} \nabla_\theta\, d_{i,t}$$

$N$ - число токенов всех ответов шага (`loss_type="dapo"`), $d_{i,t}$ - штраф KL на токене (раздел 7), $\beta = 0.04$.
То есть у нас GRPO = REINFORCE + сравнение внутри группы + штраф KL.

**Один шаг обучения:** 8 задач x 8 ответов = 64 ответа, температура 1.0. Learning rate 2e-5, 150 шагов,
около 30 секунд на шаг на GTX 1060, около 85 минут на запуск вместе с оценками held-out.

## 7. Штраф KL и что он измеряет

Штраф удерживает модель рядом с исходной, чтобы она не "сломалась" в погоне за наградой. На каждом токене ответа:

$$d_{i,t} = u - \log u - 1, \qquad u = \frac{\pi_{ref}(y_{i,t} \mid \cdot)}{\pi_\theta(y_{i,t} \mid \cdot)}$$

$\pi_{ref}$ - исходная модель (та же модель с отключённым адаптером). Если вероятности совпадают, $u = 1$ и $d = 0$.
Среднее $d$ по токенам - несмещённая оценка $KL(\pi_\theta \Vert \pi_{ref})$ (оценка k3 из статьи DeepSeekMath).
В логе это метрика `kl`, в натах на токен. Так же KL считают и логируют TRL, verl и OpenRLHF.

Что эта метрика показывает и чего не показывает:
- она измерена на задачах Countdown из обучающего батча и на ответах, которые модель сама сгенерировала.
  Это отклонение от исходной модели **на этом типе задач**. Насколько модель изменилась на задачах другого типа,
  отсюда не следует (для этого нужны отдельные замеры на других промптах или бенчмарках)
- у оценки тяжёлый хвост: один токен, который исходная модель считает в тысячи раз вероятнее, даёт выброс
  (например, 10.8 на шаге 22 в `partial_seed0`). Поэтому в отчёте KL показан ещё и скользящей медианой
- у нас KL растёт от 0 до 0.10-0.14 и дальше держится. В `partial_seed0` во время reward hacking медиана выше (0.18-0.19)

## 8. Оценка

Код: [src/evaluate.py](src/evaluate.py). Одна процедура для базы и всех адаптеров:
те же 300 задач held-out, тот же промпт, жадное декодирование (`do_sample=False`), до 256 новых токенов,
батч 32, строгая проверка из раздела 4. Метрика - строгая точность: доля ответов со статусом `correct`.
Во время обучения оценка идёт каждые 25 шагов, ответы сохраняются в `results/<запуск>/heldout_answers/`.

Сохранённые адаптеры переоценены отдельно от обучения: ответы совпали дословно 300 из 300
(раздел 5 [countdown_tests.ipynb](countdown_tests.ipynb)).

## 9. Исследование и результат

Вопрос, гипотеза, метрики и правило вывода записаны в [WORKLOG.MD](WORKLOG.MD) до экспериментальных запусков.

- **Вопрос.** Помогает ли частичная награда за близость к цели по сравнению со строгой, или модель начинает
  оптимизировать "почти попадания" в ущерб точным ответам?
- **Гипотеза.** Частичная награда уменьшит долю групп без сигнала, но точность на held-out будет не выше baseline,
  потому что при отсутствии верного ответа модель подталкивается к ближайшим неверным (простейшая лазейка - сумма всех чисел).
- **Правило вывода.** Разница заметна, только если разница средних больше разброса между seed
  и знак разницы одинаков во всех трёх парах seed.

| Условие | seed 0 | seed 1 | seed 2 | Среднее | std |
|---|---|---|---|---|---|
| база | - | - | - | 20.3% | - |
| `baseline` | 64.0% | 62.0% | 51.7% | 59.2% | 5.4 |
| `partial` | 56.7% | 62.7% | 57.7% | 59.0% | 2.6 |

- GRPO со строгой наградой работает: около +39 п.п. к базе в каждом seed.
- По правилу вывода разницы между условиями нет (знаки в парах seed: -7.3, +0.7, +6.0).
- Гипотеза подтвердилась частично: групп без сигнала меньше только в начале (шаги 1-25: 0.09-0.13 против 0.32-0.35),
  точность не выше baseline. Лазейка "сумма всех чисел" сработала в 1 запуске из 3: в `partial_seed0` на шаге 125
  так выглядели 46.7% ответов, точность упала до 20.3%, к шагу 150 восстановилась до 56.7%.
- Прирост получен почти целиком на задачах, решаемых только сложением и вычитанием (248 из 300).
  Задачи, где нужны `*` или `/`, модели почти не решают.

Подробно: разделы 7-11 [countdown_grpo.ipynb](countdown_grpo.ipynb).

## 10. Как читать логи

Логи обучения: `results/<запуск>/train_log.jsonl` (одна строка на шаг). Кривая оценки: `results/<запуск>/heldout_curve.jsonl`.

| Метрика | Что это |
|---|---|
| `reward` | средняя награда по 64 ответам шага (сэмплирование, train). При строгой награде - доля верных |
| `status/correct`, `status/wrong_value` и другие | доли статусов проверки среди 64 ответов. `status/correct` можно сравнивать между условиями |
| `frac_reward_zero_std` | доля групп без сигнала (все 8 наград равны) |
| `kl` | оценка отклонения от исходной модели, наты на токен (раздел 7) |
| `entropy` | неуверенность модели при выборе токена. Падает с 0.14-0.17 до 0.01-0.02 |
| `completions/mean_length` | средняя длина ответа в токенах (15-17 весь запуск) |
| `loss` | около 0 и не убывает: сумма преимуществ в группе равна нулю, остаётся в основном $\beta \cdot kl$ |
| `accuracy` в `heldout_curve.jsonl` | строгая точность на 300 задачах held-out, жадное декодирование |

`reward` и точность на held-out - разные измерения: первое по случайным ответам на 8 задачах train,
второе по жадным ответам на 300 фиксированных задачах. Чем увереннее модель (ниже `entropy`), тем чаще все 8 ответов
одинаковы и тем выше `frac_reward_zero_std`: обучение само себя замедляет.

## 12. Словарь

| Термин | Значение |
|---|---|
| RLVR | обучение с подкреплением с программно проверяемой наградой |
| политика $\pi_\theta$ | распределение вероятностей модели над ответами, $\theta$ - веса LoRA |
| эпизод | один ответ модели целиком (около 16 токенов), награда одна в конце |
| группа | 8 ответов модели на одну задачу |
| преимущество (advantage) | награда ответа минус средняя награда группы, делённая на std группы |
| группа без сигнала | все 8 наград равны, преимущества нулевые, группа не меняет веса |
| held-out | 300 задач, зафиксированных до обучения и используемых только для итоговой оценки |
| жадное декодирование | на каждом шаге берётся самый вероятный токен, ответ детерминирован |
| reward hacking | модель повышает награду способом, который не решает задачу |
| KL | дивергенция Кульбака-Лейблера, насколько распределение модели отличается от исходного |
